# Vadodara Road Management System — Project Guide

This guide explains the system as it is implemented in this repository: its web application, data pipeline, computer-vision model, risk-scoring method, and current data limitations.

## At a glance

The project combines a Python geospatial/road-damage pipeline with a web dashboard for exploring ward risk, planning maintenance, and tracking field reports.

The analysis is a **batch workflow**, not a continuously streaming service. It downloads or reads input data, runs road-damage detection, calculates road and ward scores, and writes files that the web app reads. The website itself is served separately by FastAPI and reads ward results from MongoDB when available, otherwise from `outputs/ward_ranking.csv`.

**Important: the current `outputs/` folder contains demo data.** The marker file `outputs/DEMO_DATA.txt` says those results were generated by `src/demo_generate.py`. That script places reproducible, synthetic damage points on the real road network and runs the normal risk-scoring step on them. These are useful for demonstrating the interface, but they are **not detections from a real Vadodara road survey**. The generator saves prior outputs under `outputs_real/` when it first switches to demo data; see [Restoring outputs](#demo-data-and-real-results).

## Models and analysis methods

### YOLOv8n road-damage detector

The computer-vision component uses **YOLOv8n**, the nano-sized Ultralytics YOLOv8 object-detection model. The pipeline starts from the `yolov8n.pt` checkpoint and fine-tunes it on the local YOLO-format road-damage dataset. It is selected as a relatively compact detector that can process many images more practically than a larger model.

The included dataset is documented as IndiaRDD2022/Roboflow: 875 training images, 434 validation images, 914 annotated boxes, and one class named `0`. The class may include potholes as well as larger cracked or ravelled road patches. Consequently, the detector is best described as a **general road-damage detector**, not a pothole-only classifier.

The configured inference confidence threshold is `0.30`. The script records each box's class, confidence, image ID, image coordinates, and bounding-box area as a fraction of the image. That area fraction is only a **severity proxy**; it does not measure pothole depth or physical area on the road.

Relevant files:

- Base checkpoint: `yolov8n.pt`
- Configured fine-tuned checkpoint: `models/pothole_best.pt`
- Training run/checkpoints: `models/train/`
- Dataset configuration: `data/raw/yolo_dataset/data.yaml`; the training step creates a local-path-adjusted `data_local.yaml`.

### DBSCAN hotspot clustering

The risk-output step uses **DBSCAN** from scikit-learn to group nearby geotagged damage detections. The configured neighborhood radius (`eps`) is 75 metres, and a cluster requires at least 3 samples. Cluster geometry is summarized and buffered to produce candidate hotspot areas.

DBSCAN does not learn from labelled training examples. It groups points by spatial density, helping combine nearby detections—such as repeated observations of a damaged location—into a hotspot. It can reduce duplicate counting but cannot guarantee that repeated Mapillary frames of the same damage are removed.

### Weighted road-risk score (not another ML model)

Each road segment receives a score from 0 to 100 assembled from configured indicators. The currently enabled components are:

1. **Damage detections per kilometre.** Detections are assigned to a nearby road segment within the configured 30-metre snap distance. The density is capped/scaled using the 95th percentile of nonzero segments so a few extreme counts do not dominate.
2. **Road importance proxy.** OSM road class is mapped to a score (for example, primary roads score higher than residential or service roads). This is not measured traffic volume.
3. **Proximity to amenities.** Distance to mapped schools, hospitals, clinics, and colleges is converted to a proximity score, capped at 500 metres. This is a proxy for nearby sensitive places; it is not complaint data.

Their configured weights are respectively 0.30, 0.20, and 0.10. Since these enabled weights sum to 0.60, the pipeline renormalizes them to sum to 1 before combining the components. Configured but currently disabled components include predicted failure (0.25, requires failure labels) and waterlogging (0.15, deferred pending elevation/waterlogging data).

Road risk is classified into Low, Medium, High, or Critical using the thresholds in `config.yaml` (25, 50, and 75). Ward risk is a road-length-weighted average of the segment scores; the pipeline also calculates detected-damage counts, total road length, and critical-priority road length for each ward.

The risk score is an explainable weighted indicator, **not a neural-network prediction of future road failure**.

## Pipeline: inputs to outputs

The five scripts in `src/` are designed to run in order. The same sequence can be started from the website's AI Pipeline page by an authorized user.

### Inputs

- Vadodara ward boundary data in `data/raw/wards/` (the workspace includes `wards_vadodara.geojson`).
- A YOLO-format dataset in `data/raw/yolo_dataset/` with training/validation images, labels, and `data.yaml`.
- Street images and metadata, either downloaded using a Mapillary access token or supplied as geotagged images with a `meta.csv`.
- OpenStreetMap road/amenity data, fetched by OSMnx when the basemap step runs.
- Settings such as the study area, metric CRS, detector configuration, score components, and hotspot thresholds in `config.yaml`.

### Steps

1. **Build basemap — `src/s01_build_basemap.py`.** Downloads the drivable OSM road graph for the configured bounding box, assigns road-class importance scores, reads ward boundaries, corrects the known swapped latitude/longitude axes in the included ward file, and projects geometry into UTM zone 43N (`EPSG:32643`) for metre-based analysis. It joins road segments to wards and records distance to nearby school/health/college POIs. Output: `data/processed/basemap.gpkg`.
2. **Train detector — `src/s02_train_detector.py`.** Rewrites dataset paths into a local `data_local.yaml`, loads `yolov8n.pt`, and calls Ultralytics training with the configured 60 epochs and 640-pixel image size. It copies the best checkpoint to `models/pothole_best.pt`, then runs validation and prints mAP@0.5 and mAP@0.5:0.95. Training duration depends on hardware; the website estimates 30–60 minutes on CPU, but actual time can vary substantially.
3. **Fetch imagery — `src/s03_fetch_mapillary.py`.** Requires `MAPILLARY_TOKEN`. It queries Mapillary zoom-14 coverage tiles, samples up to 6 images per tile, limits the selection to 500 images by default, downloads thumbnails, and writes `meta.csv`. The script can also check token access against a Berlin coverage tile using `--control`.
4. **Detect and geotag — `src/s04_detect_geotag.py`.** Loads the fine-tuned weights, runs object detection for each available image in the metadata file, and writes detections with their image locations, class/confidence, and image-area fraction to `data/processed/detections.gpkg`.
5. **Hotspots, road risk, and ward ranking — `src/s05_hotspots_and_risk.py`.** Clusters detections with DBSCAN, snaps pothole-class detections to road segments, calculates the weighted segment and ward scores, and writes `outputs/road_risk.geojson`, `outputs/hotspots.geojson`, and `outputs/ward_ranking.csv`.

The web pipeline runner records status and logs in MongoDB. It skips Mapillary steps if no Mapillary token is configured. It also skips training if `models/pothole_best.pt` already exists; run the training script directly if you intentionally want to retrain an existing model.

### Output flow into the website

After running the scripts, the web runner imports `ward_ranking.csv` into the `ward_risks` MongoDB collection and records a completed run. The ward API prefers the latest completed MongoDB run. If it cannot find one, it reads `outputs/ward_ranking.csv` directly and calculates planning estimates for those rows. Ward boundaries are served from the local GeoJSON file. Road and hotspot GeoJSON are served from `outputs/` when those files exist.

## How the website works

The website is a static single-page app served by the same FastAPI process as the API. `app/static/index.html` loads shared CSS and JavaScript; `app/static/js/app.js` handles login state, navigation, and shared UI helpers. The browser calls same-origin `/api/...` endpoints through `app/static/js/api.js`. Authenticated requests attach a bearer JWT stored in browser `localStorage`.

| Website area | What it shows or does | Why it exists |
|---|---|---|
| Sign in / Register | Creates an account or signs in; stores the returned token and user profile in the browser. | Controls access and identifies the user performing actions. |
| Dashboard | Summarizes the current ward dataset, shows a ward map preview, highest-risk wards, risk-level distribution, recent field-report activity, and a top-five ward table. | Gives staff a quick view of risk and maintenance needs. The map and risk/budget values come from the current ward records; the report chart uses submitted reports. |
| Ward Risk Map | Colors the 12 ward boundaries by priority, offers tooltips and a ward detail panel, and attempts to add the hotspot GeoJSON layer. | Makes the spatial distribution of risk easier to inspect than a table alone. |
| Priority Planning | Lists wards in risk rank order, labels proposed execution phases, and exports a CSV. Admins can apply a browser-side filter using locally saved resource limits. | Turns risk ranking into an initial work schedule, subject to resource assumptions. |
| Budget & Labour | Shows per-ward budget/workforce/duration estimates, a combined chart, and a CSV export. | Helps compare estimated work effort between wards. These figures are planning estimates, not contractor quotations. |
| Field Reports | Creates and filters reports by ward, severity, and status; engineers/admins can advance or resolve reports, and authorized staff can delete them. | Captures operational reports separately from automated image detections. |
| AI Pipeline | Shows the five pipeline steps, run history, and polled execution logs; engineers/admins can start a run. | Makes the batch analysis process visible and operable from the website. |
| Settings | Updates the user's profile; admins see team accounts and resource-constraint settings. Other settings controls save threshold/rate values in browser `localStorage`. | Provides account/team administration and prototype-level preferences. |

### API and persistence

The main API groups are `/api/auth`, `/api/wards`, `/api/reports`, `/api/pipeline`, and `/api/analytics`. FastAPI validates request/response shapes with Pydantic. MongoDB stores user accounts, reports, pipeline history, and imported ward records. Geospatial source and derived data remain in files such as GeoJSON and GeoPackage.

Passwords are hashed with PBKDF2-HMAC-SHA256 and a random salt. Login creates a signed JWT. Admin/engineer/viewer roles are used to restrict some operations, such as triggering the pipeline and changing report status.

### Estimates and important implementation caveats

- The backend currently calculates budget at **₹18/10/5/2 lakh per kilometre** for Critical/High/Medium/Low priority, workforce at **12/8/5/2 people per kilometre**, and duration using configured days-per-kilometre and workforce assumptions. These are formula-based estimates in `app/routers/wards.py`.
- Some explanatory rate labels displayed in the Budget page show different values (₹45/28/12/4 lakh per kilometre). The calculations returned by the backend use ₹18/10/5/2 lakh per kilometre; verify and reconcile these values before using either as an official estimate.
- Threshold and budget-rate controls in Settings are saved to this browser's `localStorage`; they do not currently update `config.yaml` or the backend calculation constants.
- Admin resource constraints are also saved in `localStorage`. The planning page uses them to include wards in risk order until a limit is exceeded; it is a simple greedy filter, not an optimization solver, and it does not recalculate base ward scores.
- The analytics API includes sample fallback values when it has no pipeline data (including sample priority distribution and report activity). The current dashboard instead builds its ward charts and risk cards from the ward data and report list it loads, so its display can differ from other parts of the app when there are no imported MongoDB runs.
- Road-class importance is only a proxy for traffic; amenity proximity is only a proxy for social impact; an unobserved road should not be interpreted as a road with no damage.

## Training and validating the detector

The training script expects the dataset YAML at `data/raw/yolo_dataset/data.yaml`. It overrides its dataset root and train/validation paths for the local folder layout, removes the optional test split from that generated training YAML, loads the configured base model, and trains with Ultralytics. The configuration specifies 60 epochs, 640-pixel images, and the Ultralytics defaults for other training options unless overridden by the library/configuration. The recorded training arguments also show batch size 16, pretrained weights enabled, deterministic seed 0, and validation enabled.

At the end, the script copies `models/train/weights/best.pt` to `models/pothole_best.pt` and calls model validation. Validation reports mAP@0.5 and mAP@0.5:0.95; training run logs, plots, and checkpoints are stored under `models/train/`. Check these validation metrics and inspect predictions on representative Vadodara images before relying on the model. The training imagery is mostly rural/highway dashcam imagery, so urban Vadodara conditions may differ from the training domain.

To run training by itself from the repository root:

```powershell
python -m pip install -r requirements.txt
python .\src\s02_train_detector.py
```

For the full pipeline, provide the real inputs and Mapillary token as required, then run each `s01`–`s05` script in order or trigger it from the website as an admin/engineer. Pipeline dependencies include geospatial libraries and, for Mapillary vector-tile collection, `mercantile` and `vt2geojson`; check that these optional imports are installed in the active environment if that step fails.

## Demo data and real results

`src/demo_generate.py` is explicitly for presentations and testing, not for creating survey observations. It generates reproducible synthetic damage points on the actual road network, sends them through the production scoring code, writes them under `outputs_demo/`, and switches `outputs/` to those demo results. It saves the previous `outputs/` directory to `outputs_real/` when applicable.

To restore the saved real outputs, run from the `src` directory:

```powershell
python .\demo_generate.py --restore
```

Only run the restore command after confirming that `outputs/DEMO_DATA.txt` exists and that `outputs_real/` contains the results you want to restore. The dashboard reads whichever ward data the API currently finds; it does not independently verify whether detections are real or demo-generated.

## Running the local website

The quick-start script is `run.py` in the repository root:

```powershell
python .\run.py
```

It starts Uvicorn on port 8000 and prints the local URL: [http://localhost:8000](http://localhost:8000). The app configuration defaults to MongoDB at `mongodb://localhost:27017` and database `vmc_roads`; configure `.env` or environment variables to use a different MongoDB URI/database or Mapillary token. The health endpoint is `/health`.

For cloud deployment, `render.yaml` describes the Render web service. Deployment needs a MongoDB URI and appropriate secret/environment configuration. Do not commit `.env` or API credentials.

## Known limitations

- The detector is trained on a small, single-class dataset and has a domain gap between mostly highway imagery and urban Vadodara.
- A detection's bounding-box share of an image is not physical pothole area or depth.
- Hotspot clustering reduces but does not eliminate duplicate observations.
- Risk depends on imagery coverage; no imagery means no observed detections, not proof of a damage-free road.
- OSM road class and POI distance are proxies in the absence of real traffic counts and validated complaint data.
- Predictive failure modeling, DEM-based waterlogging, rainfall features, NLP complaint analysis, and a mathematical optimization solver are not implemented in the current pipeline.
- Planning figures depend on configurable assumptions and should be validated by engineering/finance staff before operational use.
